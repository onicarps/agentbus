## 2. Product use case

AgentBus is a local, workspace-scoped event backbone for heterogeneous agent
systems. It lets IDE agents, terminal agents, notebook clients, local workers
and human gateways coordinate without requiring one orchestration framework or
a cloud service.

The intended separation is:

```text
orchestrator/controller owns lifecycle and policy
             |
             v
AgentBus stores and transports typed, correlated events
             |
             +--> agent runtimes
             +--> durable consumers and bridges
             +--> TUI/observability
             +--> human gateways such as Telegram
```

AgentBus may provide optional runner and developer-experience processes, but
the event-store core must not become the lifecycle authority for every system
that uses it.

## 3. Current shipped surface

As of v0.18.0, the repository contains:

- Python MCP and CLI event-store implementation backed by SQLite;
- typed topics, schema registry and Pydantic integration;
- artifacts/attachments and payload limits;
- trace, span, causation and correlation-related fields;
- RBAC, authentication proofs and mcpsafe policy checks;
- HITL pending approvals, SLA expiry and dead-letter events;
- publish retry, jitter and spillover resilience;
- Mission Control Textual TUI and God View observability;
- workspace process commands: `up`, `down`, `ps`, `logs`;
- Jupyter `AsyncAgentBus` and IPython magic;
- TypeScript client under `packages/js/agentbus-client`;
- Go serve/worker components and embedded platform binaries;
- wake ingress, webhook delivery and headless runner adapters;
- cooperative async suspend/resume and bounded chain behavior;
- Slack bridge and example integrations;
- MCP Python SDK v2 migration.

This breadth is why the next milestone should emphasize reliability and a
coherent contract instead of adding an unrelated integration.

## 4. Findings recorded during roadmap discovery

The following facts were observed through GitHub on 2026-08-15:

1. `pyproject.toml` and the latest tag identify v0.18.0.
2. The README and old roadmap still described v0.11 as current.
3. There were no open issues or pull requests to communicate the next scope.
4. Main CI passed, but `.github/workflows/test.yml` tested only Ubuntu with
   Python 3.11 and 3.12.
5. The latest v0.18 release rerun failed in PyPI publishing because an artifact
   with the same filename already existed. PyPI correctly forbids overwrites.
6. Go serve documents incomplete parity for HITL, SLA, RBAC, mcpsafe and the
   complete MCP tool surface.
7. The separate `onicarps/swarm` project contains a smaller AgentBus store
   rather than consuming the official package.
8. The repository exposes Python, TypeScript and Go surfaces but does not yet
   have one shared cross-language conformance suite.

These are product-hardening findings, not evidence that the core is unusable.

## 5. Review history

The original proposal prioritized:

1. v0.18 documentation and release repair;
2. durable named consumers;
3. a canonical versioned event envelope;
4. cross-platform/cross-language CI;
5. dogfooding in Swarm and Telegram;
6. later operational tooling and a deferred remote bridge.

Factory Droid agreed with the direction but returned `REVISE` because the plan
did not yet define:

- a breaking-change and deprecation strategy;
- precise consumer claim/ack/retry semantics;
- whether Go parity is required or deferred;
- whether Swarm's duplicate store is actually in scope;
- concrete platform and failure-test coverage;
- measurable acceptance criteria.

Those gaps are incorporated into this handoff. Factory Droid suggested a fixed
10,000-message/second target. This document deliberately replaces that with a
measured baseline and regression budget: AgentBus is a local coordination bus,
and correctness under crashes and contention matters before an arbitrary
throughput number.

## 6. Milestone definition

### Name

**AgentBus v0.19 — Product Hardening and Durable Consumers**

### Outcome

An operator can install AgentBus reproducibly, diagnose it, consume events with
crash-safe named subscriptions, use the same event contract from Python,
TypeScript and Go, and prove the design in the Swarm/Telegram reference system.

### Non-goals

- operating a hosted cloud service;
- replacing Kafka or Redis for high-volume distributed workloads;
- adding orchestration policy to the event-store core;
- declaring a stable v1 contract before dogfooding;
- exposing arbitrary shell or Git commands through Telegram.

## 7. Compatibility and migration policy

The preferred v0.19 strategy is additive:

- preserve existing publish and poll behavior;
- add envelope fields with safe defaults or nullable migration columns;
- keep existing topics and payloads readable;
- introduce consumer APIs alongside existing polling APIs;
- emit deprecation warnings before removing public Python/CLI/MCP behavior;
- document every database migration and test upgrades from released fixtures;
- never rewrite or silently reinterpret existing event rows;
- create a backup before any migration that cannot be reversed mechanically.

A design proposal must explicitly list any unavoidable breaking change. If a
break is necessary, ship a migration command and a compatibility window rather
than hiding it in release notes.

## 8. P0 — release and product foundation

### P0.1 Documentation alignment

- Make README, roadmap, changelog and release docs agree on the current version.
- Link this handoff from the roadmap and README.
- Distinguish shipped features from proposed scope.
- Document which Go features are parity targets and which are experiments.

Acceptance:

- no document identifies v0.11 as the current release;
- all proposed features are visibly labeled proposed;
- README installation commands work in a clean environment;
- links and example paths resolve.

### P0.2 Release idempotency and supply-chain checks

Same-tag reruns must not try to overwrite PyPI files. The workflow should:

1. build deterministic artifacts;
2. query whether each target filename already exists;
3. skip an existing artifact only when it is the same intended release;
4. fail loudly on version/hash inconsistency;
5. publish a new version only from its matching immutable tag;
6. retain provenance and attestations.

Acceptance:

- a fresh patch tag publishes all expected Python/npm/GitHub artifacts;
- rerunning that exact tag completes successfully without duplicate uploads;
- a deliberately mismatched version/tag fails before publishing;
- installation tests run against published artifacts, not only editable source.

### P0.3 CI matrix

Required coverage:

- Linux, macOS and Windows;
- Python 3.11, 3.12 and 3.13;
- current project Go toolchain (currently 1.22.x);
- supported Node LTS for the TypeScript package;
- `pytest`, `go test ./...`, TypeScript build/test and package smoke tests;
- old-database migration fixtures;
- concurrent writer, lock storm and process interruption tests;
- wheel installation checks for advertised platforms.

Not every Python/OS combination must run every expensive test. Use focused
jobs, but protect each advertised platform with at least one installation and
core behavior gate.

### P0.4 `agentbus doctor`

Proposed checks:

- workspace and configuration resolution;
- database open, `PRAGMA integrity_check`, schema/migration version;
- journal mode and busy timeout;
- basic publish/poll in an isolated diagnostic lane;
- MCP stdio startup and clean stdout framing;
- embedded Go binary discovery and executable architecture;
- schema registry and RBAC configuration validity;
- stale PID/process metadata;
- available disk space and writable state directories;
- package and runtime versions with secret redaction.

`doctor` must be read-only by default. Repair operations require an explicit,
separate command or confirmation.

## 9. P1 design — canonical event envelope

The event contract should separate routing metadata from domain payload:

```json
{
  "event_id": 123,
  "topic": "task.transitioned",
  "timestamp": "2026-08-15T12:00:00Z",
  "schema": {"name": "task.transitioned", "version": 1},
  "producer": {
    "producer_id": "codex",
    "runtime": "codex",
    "instance_id": "session-or-process-uuid"
  },
  "trace": {
    "trace_id": "...",
    "span_id": "...",
    "parent_span_id": "..."
  },
  "causation_id": 122,
  "correlation_id": "task-or-request-id",
  "idempotency_key": "...",
  "payload": {}
}
```

The exact serialized shape remains a design decision. Requirements:

- distinguish runtime identity from process/session identity;
- retain monotonic local event identity;
- define required versus optional fields;
- version payload schemas independently where appropriate;
- define unknown-field handling and forward compatibility;
- prevent secrets from entering identity or diagnostic fields;
- preserve old rows through migration/adaptation;
- use shared fixtures across Python, TypeScript and Go.

## 10. P1 design — durable consumers

### Proposed delivery guarantee

At-least-once delivery per named consumer group. Exactly-once side effects are
not promised; consumers use event IDs/idempotency keys to deduplicate effects.

### Proposed state machine

```text
AVAILABLE
   |
   | claim(group, worker, lease_ttl)
   v
CLAIMED -------------------- lease expires --------------------+
   |                                                         |
   | ack                                                     |
   v                                                         |
ACKED                                                        |
                                                             |
   | nack(error)                                             |
   v                                                         |
RETRY_WAIT -- retry_at reached --> AVAILABLE <---------------+
   |
   | attempts exhausted
   v
DEAD_LETTERED
```

### Required semantics

- consumer groups are named and workspace-scoped;
- topic filters are durable and changes are explicit/audited;
- claims are transactional and leased to a worker instance;
- expired claims become eligible again without manual repair;
- ack is idempotent;
- nack records a bounded reason and schedules policy-driven retry;
- retry exhaustion creates a per-group dead-letter record;
- out-of-order ack uses a contiguous committed watermark plus tracked gaps;
- replay never destroys original events and requires an explicit start point;
- lag reports pending count and oldest pending age;
- deletion/retention cannot remove events still required by a protected group;
- poison events cannot permanently wedge later delivery;
- CLI, Python and MCP behavior share one contract.

### Open decisions requiring a design record

1. Whether one group can change topic filters after creation.
2. Whether ordering is global event ID, per topic, or configurable.
3. Maximum claim batch and lease-extension behavior.
4. Retry policy ownership: group configuration or event metadata.
5. Dead-letter replay and attempt-counter reset semantics.
6. Retention interaction with abandoned groups.
7. Whether TypeScript/Go claim directly or through MCP/stdio.

Implementation must not begin until these decisions and the SQL transaction
boundaries are reviewed.

## 11. P1 conformance and failure testing

The conformance suite should contain language-neutral JSON fixtures and
behavior scenarios:

- publish/read canonical envelope;
- unknown optional field and newer schema version;
- duplicate idempotency key;
- two workers racing to claim the same event;
- worker crash after claim and before ack;
- duplicate ack and late ack after lease expiry;
- nack, backoff and retry exhaustion;
- poison event followed by a valid event;
- replay from event ID and timestamp;
- out-of-order acknowledgements and contiguous watermark;
- database locked/busy and abrupt process termination;
- migration from representative released database schemas.

Performance acceptance is baseline-driven:

- publish, poll and claim benchmarks are recorded on a documented machine;
- v0.19 adds no unexplained regression greater than 20% versus the baseline;
- correctness tests include at least 10,000 events and concurrent workers;
- no throughput claim is marketed without reproducible benchmark commands.

## 12. Go parity decision

Before v0.19 implementation, choose one of two paths:

### Path A — parity target

Implement and test the canonical envelope and consumer semantics in Go, then
close documented HITL/SLA/RBAC/mcpsafe gaps needed by advertised Go serve use.

### Path B — explicit experimental scope

Keep Go as a wake worker/performance experiment, clearly list unsupported
features, and route authoritative MCP/event-store operations through Python.

Do not imply full parity while leaving security or lifecycle checks absent.

## 13. Swarm dogfood integration

`onicarps/swarm` is the reference integration. It currently has a minimal local
AgentBus store. The v0.19 plan includes replacing or adapting that duplicate to
the official `okf-agentbus` package.

Required reference flow:

```text
Swarm controller persists transition
  -> official AgentBus publishes canonical event
  -> durable Telegram consumer claims event
  -> Telegram delivery succeeds and is acked
  -> authorized inbound command reaches controller
  -> controller emits correlated result event
  -> result is delivered back to Telegram
```

Acceptance:

- controller remains the only task lifecycle mutation authority;
- AgentBus owns transport/consumer state, not orchestration policy;
- gateway restarts do not duplicate completed deliveries;
- a crash before ack causes redelivery;
- correlation identifies the originating Telegram request;
- unauthorized chat content is rejected without persisting message text;
- existing Swarm lifecycle and review tests remain green.

## 14. Telegram-only operation plan

### Current capability

The existing Swarm Telegram gateway supports monitoring and limited control:

```text
/help
/tasks [status]
/status <task_id>
/events [limit]
/approvals
/ready <task_id>
/cancel <task_id> [reason]
/approve <approval_id> [note]
/reject <approval_id> [note]
```

It does not currently create tasks, start agents, run verification/review,
merge, push or accept arbitrary shell commands. Free-form text is published as
an operator event, but no general executor consumes it. Therefore, a one-time
workstation bootstrap is required before the roadmap can be operated entirely
from Telegram.

### Proposed safe command expansion

```text
/create
/schedule
/run
/verify
/review
/diff
/logs
/merge
/push
/confirm
```

Safety requirements:

- repository aliases resolve through a workstation allowlist;
- no arbitrary paths, verification commands or shell strings from chat;
- `/run`, `/merge` and `/push` require short-lived confirmation tokens;
- confirmations are actor-bound and idempotent;
- no force-push and no direct unreviewed mutation of `main`;
- verification commands come from trusted repository configuration;
- implementer and reviewer runtime instances must differ;
- every accepted, denied and failed action is correlated and audited;
- secrets and unauthorized message bodies are never logged.

### Proposed mobile task sequence

```text
/create ABUS-019-001 agentbus "Repair release pipeline and documentation" implementer
/ready ABUS-019-001
/schedule ABUS-019-001
/run ABUS-019-001
/confirm <short-lived-token>
/status ABUS-019-001
/logs ABUS-019-001
/verify ABUS-019-001
/review ABUS-019-001 factory_droid
/diff ABUS-019-001
/merge ABUS-019-001
/confirm <short-lived-token>
/push agentbus main
/confirm <short-lived-token>
```

The Mac remains the execution plane and must stay awake, connected and
authenticated. Telegram is the remote human plane, not a cloud executor.

## 16. Explicit deferrals

## 19. Definition of v0.19 complete

v0.19 is complete only when:

1. documentation and package/release versions agree;
2. release and same-tag rerun paths are green and safe;
3. advertised platform and language jobs pass;
4. compatibility and Go support boundaries are explicit;
5. `agentbus doctor` diagnoses the supported local stack;
6. envelope and durable-consumer contracts are approved and implemented;
7. crash, retry, replay, migration and contention tests pass;
8. Swarm uses the official AgentBus package for the reference path;
9. the confirmation-gated Telegram round trip passes;
10. release notes include migrations, limitations and measured baselines;
11. an independent runtime approves the final diff.

Until all gates pass, keep the milestone labeled pre-1.0 and avoid claiming
exactly-once delivery, full Go parity or remote/distributed operation.
